# Требования

Требования делятся на десять пунктов, от FR-1 до FR-10. На каждый пункт есть контрактные тесты в `tests/contract/`, а рубрика ссылается на пункты по номерам.

Через все требования проходит одно правило: модель выбирает и формулирует, а факты проверяет код. Маленькая модель путает направление связи, выдумывает коды и подставляет аргументы, которых никто не называл. Запрет в инструкции делает такие ошибки реже, а проверка в коде их исключает.

## Функциональные требования

**FR-1. Извлечение.** `extract_chunk` получает чанк и возвращает сущности и связи строго по схеме графа из [`data.md`](data.md). Модель вызывается с температурой 0 и отвечает по JSON-схеме `EXTRACTION_SCHEMA` из `assistant.infra.schemas`, в которой типы сущностей и связей заданы перечислением. Запрос содержит описание схемы с направлением каждой связи и хотя бы один пример. Имена приводятся к каноническому виду: коды прописными латинскими буквами без пробелов, названия узлов строчными. После разбора ответа код отбрасывает всё, что не подтверждается текстом:

- код, который не встречается в тексте чанка (сравнение после `normalize_code`, потому что в отчётах коды записаны небрежно)
- название узла, линейки или поставщика, которого нет в `data/vocabulary.json` (словарь возвращает `assistant.infra.config.vocabulary()`)
- связь, у которой отброшен хотя бы один конец

Число отброшенных сущностей и связей записывается в поле `dropped` результата. Если ответ модели не разбирается или не проходит проверку схемы, делается одна повторная попытка, после неё возвращается пустой результат. Функция не должна падать ни на каком ответе модели.

**FR-2. Граф.** `build_graph` объединяет результаты по всем чанкам. Одна и та же сущность из разных чанков становится одним узлом с идентификатором вида `Part:P-1042`. У ребра атрибут `weight` равен числу разных чанков, в которых связь найдена, а `sources` хранит идентификаторы этих чанков. Связи, у которых тип не из схемы или концы не соответствуют схеме, отбрасываются: например, `REPLACED_BY` соединяет только две детали. Если между двумя деталями оказались связи `REPLACED_BY` в обе стороны, остаётся та, у которой больше `weight`, а при равенстве обе отбрасываются. Число таких конфликтов записывается в атрибут графа `conflicts`.

**FR-3. Сообщества.** `detect_communities` разбивает узлы графа на сообщества алгоритмом Лувена или Лейдена с фиксированным зерном генератора. Каждый узел входит ровно в одно сообщество. `summarize_community` возвращает сводку сообщества не длиннее 150 слов: какие сущности в него входят, как они связаны, какие связи встречаются чаще всего. Все числа для сводки, например сколько раз отказывал узел, считает код по весам рёбер и передаёт модели готовыми. Модель их только формулирует.

**FR-4. Режим local.** `local_search` находит в вопросе опорные сущности без обращения к модели: коды по их виду, названия по словарю. Затем отбирает факты из графа. Если опорных сущностей две и больше, берутся факты на всех путях длиной до трёх связей между ними (направление связей при поиске пути не учитывается) и цепочки `REPLACED_BY` от деталей на этих путях. Если опорная сущность одна, берётся её окрестность на глубину до двух связей. Модель получает пронумерованный список фактов вида `E-17 -INDICATES-> пусковое реле` с документами-источниками. Модель отвечает только по этому списку. Если на пути встречается связь `REPLACED_BY`, ответ называет актуальную деталь, то есть конец цепочки замен. Если в вопросе есть код, которого нет в графе, если опорных сущностей не нашлось или список фактов пуст, функция возвращает отказ с `refused=True`, а модель не вызывается. Контекст для модели не превышает 8000 символов.

**FR-5. Режим global.** `global_search` отвечает на обзорные вопросы по сводкам сообществ в два шага. На первом шаге модель для каждой сводки даёт частичный ответ и оценку его полезности от 0 до 10 в формате JSON по схеме `MAP_SCHEMA`: `{"answer": "...", "score": 7}`. На втором шаге частичные ответы с оценкой выше 0 объединяются в итоговый ответ.

**FR-6. Инструменты.** В `tools.py` описаны пять инструментов с именами и параметрами из таблицы ниже. `TOOL_SCHEMAS` содержит их описания в формате function calling. `build_tools` возвращает словарь, где ключ – имя инструмента, а значение – функция. В описании параметра `warehouse` четыре склада заданы перечислением. Каждая функция проверяет свои аргументы до обращения к ERP: склад из списка, номер детали вида `P-1042` или `P-1042B`, количество больше нуля. При ошибке функция возвращает словарь с ключом `error` и ничего не выполняет.

| Имя | Параметры | Что делает | Откуда данные |
| --- | --- | --- | --- |
| `search_knowledge` | `question: str` | отвечает на точный вопрос по базе знаний, возвращает текст ответа, использованные факты и источники | `local_search` |
| `summarize_topic` | `question: str` | отвечает на обзорный вопрос | `global_search` |
| `check_stock` | `part_id: str`, `warehouse: str` | возвращает остаток детали на складе и признак `discontinued` | ERP |
| `get_price` | `part_id: str` | возвращает цену детали в рублях и признак `discontinued` | ERP |
| `create_service_order` | `part_id: str`, `warehouse: str`, `qty: int`, `model: str` | создаёт заказ детали | ERP, нужно подтверждение |

**FR-7. Цикл агента.** `run_agent` ведёт диалог с моделью в цикле «рассуждение, вызов инструмента, наблюдение». Описания инструментов из `TOOL_SCHEMAS` передаются модели в каждом запросе. Агент делает не больше `max_steps` вызовов инструментов. Каждый вызов записывается в `steps` с аргументами и результатом. Если модель назвала несуществующий инструмент или передала неверные аргументы, ошибка возвращается модели как наблюдение, а цикл продолжается. Сверх этого агент сам проверяет три вещи:

- номер детали в аргументах должен встречаться в вопросе пользователя или в результате предыдущего инструмента. Иначе вызов не выполняется, а модель получает наблюдение с подсказкой сначала вызвать `search_knowledge`
- количество в заказе должно быть названо пользователем. Если его нет в вопросе, агент не вызывает `create_service_order`, а возвращает уточняющий вопрос
- вызов с теми же аргументами второй раз не выполняется, агент возвращает прежний результат

Если лимит шагов исчерпан, агент возвращает лучший доступный ответ и прямо сообщает, что не закончил.

**FR-8. Отказы ERP.** При исключении `ErpUnavailable` вызов повторяется до двух раз. Если все попытки неудачны, шаг записывается с заполненным полем `error`, а в ответе пользователю сказано, что данные ERP получить не удалось. Остатки и цены при этом не выдумываются. Клиент ERP различает три исхода: значение получено, данных нет, сервис недоступен. Они описаны в [`data.md`](data.md). Ответ называет исход как есть: «данных по складу нет» не превращается в «остаток ноль».

**FR-9. Подтверждение действий.** `create_service_order` меняет данные в ERP, поэтому без `confirm=True` не выполняется. Вместо этого агент останавливается и возвращает `needs_confirmation=True` и `pending_action` вида `{"tool": "create_service_order", "args": {...}}` с предлагаемыми аргументами. При `confirm=True` заказ создаётся, а его номер попадает в ответ.

**FR-10. Источники и честный отказ.** Каждый ответ в режимах `local`, `global` и `agent` содержит список документов-источников в поле `sources`. Если в базе знаний нет данных для ответа, ассистент так и пишет: «в базе знаний не найдено». Номера деталей, остатки и цены, которых нет в контексте или в ответах инструментов, в ответе появляться не должны. Агент проверяет это кодом перед выдачей ответа: каждый код, каждая цена и каждый остаток из ответа должны встречаться в вопросе или в результатах инструментов. Если проверка не прошла, агент один раз просит модель исправить ответ, а после второй неудачи возвращает отказ.

## Что выдаётся готовым

Эти функции и типы лежат в `assistant.infra`. Пользоваться ими можно и нужно, менять нельзя.

| Где | Что |
| --- | --- |
| `schemas` | типы `Chunk`, `Entity`, `Relation`, `ExtractionResult`, `Community`, `KnowledgeBase`, `Answer`, `ToolStep`, `AgentResult`, схема графа `ENTITY_TYPES` и `RELATION_SIGNATURES`, JSON-схемы `EXTRACTION_SCHEMA` и `MAP_SCHEMA` |
| `llm` | `LLMClient` с методами `chat` и `embed`, типы `LLMResponse` и `ToolCall`, функция `tool_message` для истории диалога |
| `grounding` | `find_codes`, `normalize_code`, `code_type`, `find_names`, `canonical_name` |
| `config` | `vocabulary()` – словарь названий |
| `erp_client` | `ErpClient` и исключения `ErpNotFound`, `ErpUnavailable`, `ErpRejected` |
| `testing` | `FakeLLM` – подставная модель для ваших собственных тестов |

`LLMClient` уже настроен на воспроизводимую генерацию: температура 0 и фиксированное зерно. Ответ по JSON-схеме включается параметром `json_schema`, инструменты – параметром `tools`.

## Интерфейсы

Сигнатуры функций, которые вы реализуете. Менять их нельзя.

```python
# src/assistant/graphrag/extraction.py
def extract_chunk(chunk: Chunk, llm: LLMClient) -> ExtractionResult: ...

# src/assistant/graphrag/graph_builder.py
def build_graph(results: list[ExtractionResult]) -> nx.DiGraph: ...

# src/assistant/graphrag/communities.py
def detect_communities(graph: nx.DiGraph) -> list[Community]: ...
def summarize_community(community: Community, graph: nx.DiGraph, llm: LLMClient) -> str: ...

# src/assistant/graphrag/search.py
def local_search(question: str, kb: KnowledgeBase, llm: LLMClient) -> Answer: ...
def global_search(question: str, kb: KnowledgeBase, llm: LLMClient) -> Answer: ...

# src/assistant/agent/tools.py
TOOL_SCHEMAS: list[dict]
def build_tools(kb: KnowledgeBase, llm: LLMClient, erp: ErpClient) -> dict[str, Callable[..., dict]]: ...

# src/assistant/agent/agent.py
def run_agent(
    question: str,
    llm: LLMClient,
    tools: dict[str, Callable[..., dict]],
    *,
    max_steps: int = 6,
    confirm: bool = False,
) -> AgentResult: ...
```

## Ограничения

- Не меняются: `src/assistant/infra/`, `tests/contract/`, `tests/infra/`, `erp/`, `data/`, `Dockerfile`, `docker-compose.yml`, `Makefile`, `pyproject.toml`. Если вы нашли в них ошибку, напишите преподавателю.
- Все обращения к модели идут через выданный `LLMClient`. Он кеширует ответы и считает вызовы и токены. Обращения в обход него ломают и воспроизводимость, и подсчёт стоимости.
- Ядро пишется самостоятельно. LangChain, LlamaIndex, библиотека `graphrag` и их аналоги не используются. Разрешены `networkx`, `pydantic`, `httpx`, `numpy` и стандартная библиотека Python. Другие зависимости согласуются с преподавателем.
- Новые сервисы и базы данных не добавляются. Граф хранится в памяти и сохраняется в JSON.
- Код проходит `make lint`.
- Ключи и токены в репозиторий не попадают.

## Что не входит в задачу

- дообучение моделей
- веб-интерфейс
- графовая база данных
- поддержка других языков и других форматов документов
- изменение инфраструктуры репозитория
