# Требования

Десять требований, от FR-1 до FR-10. На каждое есть контрактные тесты в `tests/contract/`, а критерии оценки ссылаются на требования по номерам.

Общее правило: модель выбирает и формулирует, а факты проверяет код.

## Граф знаний

**FR-1. Извлечение.** `extract_chunk(chunk, llm)` возвращает сущности и связи чанка по схеме из [`data.md`](data.md).

- Модель вызывается с `json_schema=EXTRACTION_SCHEMA`. Запрос описывает схему с направлением каждой связи и содержит хотя бы один пример
- Имена приводятся к каноническому виду: коды как `AR-210` и `P-1042B`, названия как в словаре
- В результате остаются коды, которые есть в тексте чанка, и названия из словаря. Сравнение кодов идёт после `normalize_code`. Связь остаётся, если остались оба её конца
- Число отброшенных сущностей и связей записывается в поле `dropped`
- Если ответ модели не разбирается по схеме, функция делает одну повторную попытку, а после второй неудачи возвращает пустой результат

**FR-2. Граф.** `build_graph(results)` объединяет результаты по всем чанкам в один `nx.DiGraph`.

- Узел: идентификатор вида `Part:P-1042`, атрибуты `type`, `name`, `sources`
- Ребро: атрибуты `type`, `weight` и `sources`. Вес равен числу разных чанков, в которых связь найдена
- В граф попадают связи, которые соответствуют схеме: `Relation.matches_schema()`
- Если две детали связаны `REPLACED_BY` в обе стороны, остаётся связь с большим весом, при равных весах удаляются обе. Число таких случаев записывается в `graph.graph["conflicts"]`

**FR-3. Сообщества.** `detect_communities(graph)` разбивает узлы алгоритмом Лувена с фиксированным `seed`. Каждый узел входит ровно в одно сообщество, номера сообществ идут с нуля. `summarize_community(community, graph, llm)` одним вызовом модели пишет сводку длиной до 150 слов. Числа для сводки считает код по весам рёбер и передаёт модели готовыми.

## Поиск

**FR-4. Режим local.** `local_search(question, kb, llm)` отвечает по фактам из графа.

- Опорные сущности ищутся кодом: коды через `find_codes`, названия через `find_names`
- Две и больше опорных сущности: берутся факты на всех путях длиной до трёх связей между ними, направление связей при поиске пути игнорируется. К ним добавляются цепочки `REPLACED_BY` от деталей на этих путях
- Одна опорная сущность: берётся её окрестность на глубину до двух связей
- Модель получает пронумерованный список фактов вида `E-17 -INDICATES-> пусковое реле` объёмом до 8000 символов и отвечает по нему. Если в фактах есть замена, ответ называет последнюю деталь цепочки
- Если код из вопроса отсутствует в графе или фактов не нашлось, функция сразу возвращает `Answer(..., refused=True)`, без вызова модели

**FR-5. Режим global.** `global_search(question, kb, llm)` отвечает по сводкам сообществ в два шага.

- Шаг map: для каждой сводки модель возвращает JSON по схеме `MAP_SCHEMA`, например `{"answer": "...", "score": 7}`. Нечитаемый частичный ответ пропускается
- Шаг reduce: частичные ответы с оценкой выше 0 объединяются одним вызовом модели
- Если таких ответов нет, функция возвращает `Answer(..., refused=True)`

## Агент

**FR-6. Инструменты.** `TOOL_SCHEMAS` описывает пять инструментов в формате function calling, склады в параметре `warehouse` заданы перечислением. `build_tools(kb, llm, erp)` возвращает словарь «имя -> функция».

| Имя | Параметры | Что возвращает |
| --- | --- | --- |
| `search_knowledge` | `question` | результат `local_search`: `answer`, `facts`, `sources`, `refused` |
| `summarize_topic` | `question` | результат `global_search`: `answer`, `sources`, `refused` |
| `check_stock` | `part_id`, `warehouse` | остаток детали на складе и признак `discontinued` |
| `get_price` | `part_id` | цену детали в рублях и признак `discontinued` |
| `create_service_order` | `part_id`, `warehouse`, `qty`, `model` | номер созданного заказа |

Каждая функция сначала проверяет аргументы: склад из списка, номер детали вида `P-1042` или `P-1042B`, количество больше нуля. При ошибке проверки и при исключениях `ErpNotFound` и `ErpRejected` она возвращает словарь с ключом `error`.

**FR-7. Цикл агента.** `run_agent(question, llm, tools, max_steps=6, confirm=False)` ведёт диалог с моделью, передаёт ей `TOOL_SCHEMAS` и выполняет до `max_steps` вызовов инструментов. Каждый вызов записывается в `steps`.

- Неизвестный инструмент и нечитаемые аргументы возвращаются модели как ошибка, цикл продолжается
- Номер детали в аргументах должен встречаться в вопросе или в результатах предыдущих инструментов. Иначе вызов отклоняется, а модель получает подсказку вызвать `search_knowledge`
- Количество в заказе должно быть названо в вопросе. Иначе агент возвращает уточняющий вопрос
- Повторный вызов с теми же аргументами получает прежний результат
- Когда лимит шагов исчерпан, агент возвращает то, что успел узнать, и сообщает, что работа прервана

**FR-8. Отказы ERP.** При `ErpUnavailable` вызов повторяется ещё два раза. После трёх неудач шаг записывается с заполненным `error`, а ответ сообщает, что данные ERP получить не удалось. Три исхода запроса к ERP из [`data.md`](data.md) в ответе остаются различимыми: «данных нет» и «остаток 0» – разные ответы.

**FR-9. Подтверждение.** Заказ создаётся только при `confirm=True`, и его номер попадает в ответ. При `confirm=False` агент останавливается и возвращает `needs_confirmation=True` и `pending_action` вида `{"tool": "create_service_order", "args": {...}}`.

**FR-10. Источники и отказ.** Ответ в режимах `local`, `global` и `agent` содержит документы-источники в поле `sources`. Когда данных для ответа нет, ассистент пишет «в базе знаний не найдено» и возвращает `refused=True`. Перед выдачей ответа агент сверяет его с вопросом и результатами инструментов: каждый код, каждая цена и каждый остаток должны там встречаться. При расхождении агент один раз просит модель исправить ответ, после второго расхождения возвращает отказ.

## Готовые типы и функции

Сигнатуры ваших функций записаны в заготовках. Типы и готовые функции лежат в `assistant.infra`:

| Модуль | Что в нём |
| --- | --- |
| `schemas` | типы данных, схема графа `ENTITY_TYPES` и `RELATION_SIGNATURES`, JSON-схемы `EXTRACTION_SCHEMA` и `MAP_SCHEMA` |
| `llm` | `LLMClient` с методами `chat` и `embed`, `LLMResponse`, `ToolCall`, `tool_message` |
| `grounding` | `find_codes`, `normalize_code`, `code_type`, `find_names`, `canonical_name` |
| `config` | `vocabulary()` – словарь названий |
| `erp_client` | `ErpClient` и исключения `ErpNotFound`, `ErpUnavailable`, `ErpRejected` |
| `testing` | `FakeLLM` – подставная модель для ваших тестов |

## Правила работы с кодом

- Ваш код лежит в `src/assistant/graphrag/` и `src/assistant/agent/`. Сигнатуры из заготовок и остальные файлы репозитория остаются как есть. Об ошибке в них сообщите преподавателю
- Все обращения к модели идут через `LLMClient`: он кеширует ответы и считает вызовы и токены. Генерация в нём воспроизводимая, с температурой 0 и фиксированным зерном
- Ядро пишется на `networkx`, `pydantic`, `httpx`, `numpy` и стандартной библиотеке Python. Другие зависимости согласуются с преподавателем
- Граф хранится в памяти и сохраняется в JSON
- Код проходит `make lint`
- Ключи и токены хранятся в `.env`
