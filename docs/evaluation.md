# Оценка

Оценка сравнивает строки и не использует модель-судью: ответы в проекте строятся вокруг кодов, чисел и названий из словаря, поэтому их можно проверить точно.

## Команды

```bash
make eval MODE=baseline   # плоский RAG
make eval MODE=local      # ваш local_search
make eval MODE=global     # ваш global_search
make eval MODE=agent      # ваш агент с инструментами
make eval-all             # четыре режима подряд
make eval-extraction      # качество извлечения на эталоне
```

Каждая команда печатает итоговую строку и пишет отчёт в `artifacts/`:

| Файл | Что в нём |
| --- | --- |
| `eval_baseline.json`, `eval_local.json`, `eval_global.json`, `eval_agent.json` | раздел `summary` с метриками режима и раздел `rows` с ответом на каждый вопрос |
| `eval_extraction.json` | Precision и Recall по сущностям и связям |
| `index_stats.json` | размер графа и стоимость индексации, пишется командой `make index` |

Все режимы отвечают на одни и те же 24 вопроса. Плоский RAG и поиск по графу не умеют обращаться в ERP, поэтому на вопросах типа `tool` они заведомо ошибаются. Это ожидаемо и в таблице результатов выглядит как 0.

## Метрики ответов

**Доля верных ответов.** Поля `accuracy` и `by_type`. Ответ верен, если в нём есть все ключевые факты вопроса.

- Код сравнивается целиком и в каноническом виде. Ответ «P-1042B» не засчитывается за факт «P-1042», а «p-1042b» засчитывается за «P-1042B»
- Число должно стоять отдельно. Пробелы между разрядами не мешают: «2 630» и «2630» равны
- Название узла засчитывается в именительном и родительном падеже: «пусковое реле» и «пускового реле»

Для вопросов типа `tool` дополнительно проверяется трасса агента: в ней должны быть ожидаемые вызовы с точно такими аргументами. Если вопрос просит оформить заказ, агент должен остановиться и вернуть его на подтверждение, а не создать.

Для вопросов типа `refusal` ответ верен, если `refused` равно `True` и в тексте нет номеров деталей, цен и остатков.

**Выдуманные факты.** Поле `fabricated_rate`: доля ответов, в которых есть код, отсутствующий и в корпусе, и в вопросе, либо цена или остаток, которых нет в результатах инструментов этого диалога. Чем ближе к нулю, тем лучше. У каждого ответа в `rows` выдуманные факты перечислены в поле `fabricated`.

**Recall источников.** Поле `source_recall`: какая доля нужных документов попала в `sources` ответа. Ответ складывается из нескольких связей графа, и у каждой связи есть группа документов, где она записана. Группа считается найденной, если в `sources` есть хотя бы один её документ. Для обзорных вопросов метрика не считается.

**Отклонённые вызовы.** Поле `rejected_calls_rate`: доля вызовов инструментов, которые не прошли проверку аргументов или закончились ошибкой.

**Стоимость.** Поля `llm_calls_per_question` и `tokens_per_question`. Вызов, взятый из кеша, считается так же, как обычный, поэтому стоимость режимов можно сравнивать при любом состоянии кеша.

## Метрики извлечения

Команда `make eval-extraction` запускает `extract_chunk` на 16 документах с эталоном и считает две метрики, отдельно по сущностям и по связям.

Пусть $E$ – множество извлечённых связей, $G$ – множество обязательных связей эталона, а $O$ – множество необязательных, но верных связей.

$$\text{Precision} = \frac{|E \cap (G \cup O)|}{|E|}, \qquad \text{Recall} = \frac{|E \cap G|}{|G|}$$

Precision показывает, какая доля извлечённого верна. Recall показывает, какая доля обязательного найдена. Связь из $O$ в тексте прямо не названа, но следует из него: за неё Precision не снижается, а в Recall она не входит.

Поле `dropped` в отчёте – сколько сущностей и связей отбросили ваши проверки из FR-1. Большое число здесь означает, что модель часто выдумывает, и стоит посмотреть на запрос.

## Как читать результаты

Жёстких порогов качества нет. Graph RAG не обязан выиграть у плоского RAG на всех типах вопросов, и он заведомо дороже. Оценивается система, которая работает по требованиям, и честный разбор того, где граф помогает, а где нет.

Для ориентира: плоский RAG на модели по умолчанию отвечает верно на 12 открытых вопросов из 24. Он справляется со всеми вопросами типа `local` и `refusal`, с четырьмя из семи `multihop` и ни с одним `global` и `tool`.

Обзорные вопросы оцениваются по названиям и кодам, а не по точным числам отказов. Извлечение у маленькой модели неполное, и точные числа у разных решений расходятся.

Скрытые вопросы преподаватель запускает той же командой с другим файлом:

```bash
python -m assistant eval --mode agent --questions <файл>
```
