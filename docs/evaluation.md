# Оценка

Оценка сравнивает строки. Ответы в проекте строятся вокруг кодов, чисел и названий из словаря, поэтому их можно проверить точно.

## Команды

```bash
make eval MODE=baseline   # плоский RAG
make eval MODE=local      # ваш local_search
make eval MODE=global     # ваш global_search
make eval MODE=agent      # ваш агент с инструментами
make eval-all             # четыре режима подряд
make eval-extraction      # качество извлечения на эталоне
```

Каждая команда печатает итоговую строку и пишет отчёт в `artifacts/`:

| Файл | Что в нём |
| --- | --- |
| `eval_baseline.json`, `eval_local.json`, `eval_global.json`, `eval_agent.json` | раздел `summary` с метриками режима и раздел `rows` с ответом на каждый вопрос |
| `eval_extraction.json` | Precision и Recall по сущностям и связям |
| `index_stats.json` | размер графа и стоимость индексации, пишется командой `make index` |

Все режимы отвечают на одни и те же 24 вопроса. В ERP обращается только агент, поэтому у остальных режимов доля верных ответов на вопросах типа `tool` равна 0.

## Метрики ответов

**Доля верных ответов.** Поля `accuracy` и `by_type`. Ответ верен, если в нём есть все ключевые факты вопроса.

- Код сравнивается целиком и в каноническом виде: «p-1042b» засчитывается за «P-1042B», а «P-1042» и «P-1042B» – разные коды
- Число стоит в ответе отдельно от кодов и слов, «2 630» и «2630» равны
- Название узла засчитывается в именительном и родительном падеже: «пусковое реле» и «пускового реле»

Для вопросов типа `tool` дополнительно проверяется трасса агента: в ней должны быть ожидаемые вызовы с точно такими аргументами. Если вопрос просит оформить заказ, агент останавливается и возвращает его на подтверждение.

Для вопросов типа `refusal` ответ верен, если `refused` равно `True`, а номера деталей в тексте взяты только из вопроса. Цена или остаток в таком ответе считается ошибкой.

**Выдуманные факты.** Поле `fabricated_rate`: доля ответов, в которых есть код вне корпуса и вопроса либо цена или остаток вне результатов инструментов этого диалога. Чем ближе к нулю, тем лучше. У каждого ответа в `rows` выдуманные факты перечислены в поле `fabricated`.

**Recall источников.** Поле `source_recall`: какая доля нужных документов попала в `sources` ответа. Ответ складывается из нескольких связей графа, и у каждой связи есть группа документов, где она записана. Группа считается найденной, если в `sources` есть хотя бы один её документ. Метрика считается по вопросам, у которых в поле `source_groups` перечислены группы.

**Отклонённые вызовы.** Поле `rejected_calls_rate`: доля вызовов инструментов, которые остановила проверка аргументов или которые закончились ошибкой.

**Стоимость.** Поля `llm_calls_per_question` и `tokens_per_question`. Вызов, взятый из кеша, считается так же, как обычный, поэтому стоимость режимов можно сравнивать при любом состоянии кеша.

## Метрики извлечения

Команда `make eval-extraction` запускает `extract_chunk` на 16 документах с эталоном и считает две метрики, отдельно по сущностям и по связям.

Это Precision и Recall из [`theory.md`](theory.md) с одним уточнением: эталон делится на обязательные и необязательные связи. Пусть $E$ – множество извлечённых связей, $G$ – множество обязательных связей эталона, а $O$ – множество необязательных связей.

$$\text{Precision} = \frac{|E \cap (G \cup O)|}{|E|}, \qquad \text{Recall} = \frac{|E \cap G|}{|G|}$$

Precision показывает, какая доля извлечённого верна. Recall показывает, какая доля обязательного найдена. Связь из $O$ следует из текста косвенно. Если она найдена, Precision считает её верной. Recall считается только по $G$.

Поле `dropped` в отчёте – сколько сущностей и связей отбросили ваши проверки из FR-1. Большое число здесь означает, что модель часто выдумывает, и стоит посмотреть на запрос.

## Как читать результаты

Оценивается система, которая работает по требованиям, и честный разбор того, на каких вопросах граф помогает и сколько это стоит.

Для ориентира: плоский RAG на модели по умолчанию отвечает верно на 12 открытых вопросов из 24. Это все вопросы типов `local` и `refusal` и четыре из семи `multihop`.

Обзорные вопросы оцениваются по названиям и кодам: какой узел отказывает чаще всего, у какой модели больше отказов.

Скрытые вопросы преподаватель запускает той же командой с другим файлом:

```bash
python -m assistant eval --mode agent --questions <файл>
```
